# 20261020-用户态`rootkit`

## 问题描述

1. `w`的`WHAT`列只显示`ssh`，无法输出具体的`ssh`目标。
2. 当文件夹内存在悬空链接的时候使用`ls`会跳过链接，同时提示`No such file or directory`。
3. `ldd`和`strace`会被拦截，同时提示`Operation not permitted`。
   但是使用`/lib64/ld-linux-x86-64.so.2 --list`能正常实现`ldd`功能，使用`/lib64/ld-linux-x86-64.so.2 /bin/strace`能正常实现`strace`功能。
   此外将`strace`复制到本地并改名也能正常使用，说明是按照命令的名称来进行拦截的。

## 初步排查

推测对`ldd`和`strace`的拦截发生在`execve`，使用`/lib64/ld-linux-x86-64.so.2`启动或者改名就能绕过这种按名称拦截特定命令的黑名单机制。

即存在对所有动态程序生效的用户态注入。

因此首先检查`$LD_PRELOAD`与`/etc/ld.so.preload`：
```bash
>>> echo $LD_PRELOAD

>>> busybox ls /etc/ld.so.preload
    ls: /etc/ld.so.preload: No such file or directory
```
两者均无异常，而注入对所有动态程序生效，因此怀疑加载器本体被篡改。

使用静态编译的不受动态链接器影响的`busybox`将`mgt`的`/lib64/ld-linux-x86-64.so.2`复制到家目录并在`GPU`上进行对比后发现：
```bash
>>> diff <(strings ld-linux-x86-64.so.2) <(strings /lib64/ld-linux-x86-64.so.2)
    1169c1169
    < /lib/lsbhnyoeumqgk
    ---
    > /etc/ld.so.preload
```

而在`mgt`端则发现：
```bash
>>> busybox cat /lib/lsbhnyoeumqgk 
    /lib/libxcb-xy/liblibxcb-xy.so.x86_64
```

此外，在行为已被篡改的`/bin/ls`依赖项内发现了可疑的`/lib/libxcb-xy/liblibxcb-xy.so.x86_64`：

由此推测，`mgt`上每个动态程序启动时，被改过的`/lib64/ld-linux-x86-64.so.2`根据`/lib/lsbhnyoeumqgk`注入`/lib/libxcb-xy/liblibxcb-xy.so.x86_64`，从而导致了上述一系列现象，包括但不限于：
1. 将`opendir`对`/proc/<pid>`的目录打开重定向到`/bin/gtester-repv`，并将`/proc/<pid>/cmdline`的内容截断为程序名
2. `stat`/`lstat`做隐藏判定时对悬空链接透传了`stat`的`ENOENT`，由此导致`No such file or directory`
3. 在`execve`内按名称拦截`strace`/`ldd`等命令，命中返回`EPERM`，即`Operation not permitted`
4. 按`/bin/json_refok`中的`GID`隐藏`open`/`stat`，命中则同样返回`ENOENT`

## 短期处理方案

对`/lib/libxcb-xy/liblibxcb-xy.so.x86_64`的全量`strings`和静态分析确定其属于`Bedevil`谱系。

并且`/lib/libxcb-xy`不存在的话会触发`rknomore`，针对服务器所有进程的恶意注入行为会立即全部停止。

因此短期内考虑分两步进行处理：
1. 将`/lib/libxcb-xy`以及上述所有排查出来的恶性文件全都隔离封存起来
2. 将`GPU`节点健康的`/lib64/ld-linux-x86-64.so.2`移植到`mgt`节点（实际采用的是`yum reinstall glibc`）
